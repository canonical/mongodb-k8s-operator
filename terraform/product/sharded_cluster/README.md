# Terraform module for MongoDB sharded cluster

This module deploys a MongoDB 6 sharded cluster with the Terraform Juju provider.

## Requirements

| Name          | Version  |
| ------------- | -------- |
| Terraform     | >= 1.11  |
| Juju provider | >= 2.2.1 |

## Modules

| Name               | Source                                                |
| ------------------ | ----------------------------------------------------- |
| config_and_routing | ../../components/config_and_routing                   |
| data_integrator    | canonical/data-integrator, `main`                     |
| shards             | ../../charms/mongodb                                  |
| s3_integrator      | canonical/object-storage-integrator S3 module, `main` |

### Sensitive configurations and secrets

S3 credentials are sensitive and ephemeral. Both keys share one Juju secret written with `value_wo`, keeping credentials out of state and saved plans. Supply `TF_VAR_s3_access_key` and `TF_VAR_s3_secret_key` at plan and apply. Passing credentials through `-var` may expose them in shell history; avoid credential `.tfvars` files. Forwarding root modules must also declare their keys sensitive and ephemeral.

| Version         | Credential    | Result                           |
| --------------- | ------------- | -------------------------------- |
| `0` (default)   | unset         | No managed secret                |
| `1`             | both keys set | Secret created, revision 1       |
| `2`             | new keys      | In-place rotation, revision 2    |
| `2` (unchanged) | unset         | No secret update                 |
| `0` again       | unset         | Managed secret and grant removed |
| `1` again       | both keys set | New secret, revision 1           |

Configure `backups_integrator` before setting a nonzero `s3_secret_version`. Keep the version in non-sensitive configuration. Rotate by changing both keys and incrementing the version together. Changing credentials alone has no effect. Unrelated plans and applies work with credentials unset.

Alternatively, supply `s3_secret_uri` for an existing secret in the S3 integrator's model containing `access-key` and `secret-key`. It overrides credentials and version: the module creates no secret, grants the integrator access, and supplies the URI through its `credentials` config. Both `secret:<id>` and `secret://<model-uuid>/<id>` are supported. Secrets are used only when the integrator is enabled.

When switching from a managed secret to a URI, use a separate existing secret: Terraform destroys the previously managed secret. The supplied secret's contents and lifecycle remain externally managed.
